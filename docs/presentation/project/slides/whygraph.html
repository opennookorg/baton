Technical · impact of HydraDB

Why this needs a graph

Answers are multi-hop

An issue reaches a team through past fixes: entity → issue → team. A lookup table sees one hop.

Learning edits the graph

Reweighting changes one link’s cost. Shortcuts add entity → team links. Gap filling adds older issues as nodes.

One query scores every team

One weighted algo.MSpaths call ranks all 22 teams and returns the cheapest path as the reason.

The plain-store baseline is 58.0%

count_only is the same data kept as counts. The 9 extra points come from what the graph does with its links.

CALL algo.MSpaths({

sourceLabel: 'Entity',

sourceValues: [issue entities],

targetLabel: 'Team',

targetValues: [all 22 teams],

relTypes: ['ROUTES_TO', 'SEEN_IN',

'OWNED_BY', 'SAME_AS'],

relDirection: 'outgoing',

maxLen: 3, pathCount: 3,

weightProp: 'cost'

}) YIELD path, pathWeight

score(team) = Σ 1 / pathWeight

From baton/db.py · learning writes go back as batched UNWIND … MERGE

The judges asked whether the graph is doing real work, and whether this would fall apart on a plain store. Three reasons it would. Answers are multi-hop: entity to past issue to team. Learning is graph surgery: reweighting changes one link's cost, shortcuts add new links, gap filling adds nodes. And one weighted path query scores every team and gives the reason. The count_only line is the plain-store version of the same data, and it stops at 58 percent. Learning writes go back to HydraDB through batched UNWIND MERGE statements.
