Technical · impact of HydraDB

Why this needs a graph

Answers are multi-hop

An issue reaches a team through past fixes: entity → issue → team. A lookup table sees one hop.

Learning edits the graph

Reweighting changes one link’s cost. Shortcuts add entity → team links. Gap filling adds older issues as nodes.

One query scores every team

One weighted algo.MSpaths call ranks all 22 teams and returns the cheapest path as the reason.

Against a plain store, measured

Naive Bayes with no graph ties Baton on the fixed test set (70.3% vs 70.0%). Routing live, Baton wins 70.0% to 64.5% (McNemar z = 5.8) and relearns a reorg faster.

CALL algo.MSpaths({

sourceLabel: 'Entity',

sourceValues: [issue entities],

targetLabel: 'Team',

targetValues: [all 22 teams],

relTypes: ['ROUTES_TO', 'SEEN_IN',

'OWNED_BY', 'SAME_AS'],

relDirection: 'outgoing',

maxLen: 3, pathCount: 3,

weightProp: 'cost'

}) YIELD path, pathWeight

score(team) = Σ 1 / pathWeight

÷ teams the path's entity reaches

From baton/db.py · learning writes go back as batched UNWIND … MERGE

The judges asked whether the graph is doing real work, and whether this would fall apart on a plain store. Three reasons it would. Answers are multi-hop: entity to past issue to team. Learning is graph surgery: reweighting changes one link's cost, shortcuts add new links, gap filling adds nodes. And one weighted path query scores every team and gives the reason. We also measured it. Naive Bayes on the same words with no graph ties Baton on the fixed test set, 70.3 against 70.0, which is within noise. Routing live, each issue before its answer is known, Baton wins 70 to 64.5 over 1,700 issues, far outside chance, and after a reorg it is at 73 percent on the moved team when naive Bayes is at 39. And it gives the path as the reason. Learning writes go back to HydraDB through batched UNWIND MERGE statements.
