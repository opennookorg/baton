Technical · the right metrics

Scored the way it would be used

Split by time

The oldest 1,700 of 2,000 Kubernetes issues stream in, 100 at a time. The newest 300 are only scored.

Top-1 and top-3

Right when the top team, or one of the top three, is one of the issue’s sig/ labels.

No label leaks

Title tags like “[sig-node]” are stripped first: 360 of 1,700 learning and 98 of 300 test issues had one.

Tuned on the stream

Every learning value was picked on learning-stream accuracy. The test set was never scored while tuning.

Two baselines

frozen: built once from 200 issues, never updated. count_only: every issue added, raw counts.

One command

uv run python -m eval.run_curve reruns all eight lines live on HydraDB.

Source: results/curve.json, results/tuning.json

Judges asked for the right metrics, not vanity numbers. So: a time split, the way it would be used, with the newest 300 issues held out. Top-1 is what you need to route automatically, top-3 is what a human triager sees. Sig mentions in titles are hidden so the answer cannot leak. Every learning value was tuned on the learning stream only. And there are two baselines: a frozen graph, which is what an ownership list is, and count-only, which is the same data with no learning.
